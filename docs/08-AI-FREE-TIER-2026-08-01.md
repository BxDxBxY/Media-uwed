# The content pipeline on OpenRouter's free tier (2026-08-01)

Covers the whole path a story travels — RSS ingestion, scraping, topical triage against the
admin's editorial brief, the editorial pass, and what the public pages do with the result —
under one hard constraint: the deployment uses an OpenRouter account with **no purchased
credit**, so only `:free` model variants are usable and the daily request budget is the
scarce resource that shapes every design decision below.

The single most consequential finding: **the pipeline had nothing to rewrite.** The scraper
returned zero characters for every configured source, so the model was inventing articles
from headlines. That is §2.8, and it is the reason the rest of the ingestion work exists.

Previous document: [07-HARDENING-2026-07-31.md](07-HARDENING-2026-07-31.md).

---

## 1. What the free tier actually allows

Confirmed against OpenRouter's rate-limit documentation on 2026-08-01:

| | Limit |
|---|---|
| Requests per minute | 20, across all `:free` models |
| Requests per day | **50** while lifetime credit purchased is under $10 |
| Requests per day | 1000 once $10 has ever been purchased |
| Response when exceeded | `429`, message `Rate limit exceeded` |

Limits are governed per user, not per key: extra accounts or keys do not raise them.

The pipeline spends **one request per article** (the single editorial pass produces EN, RU
and UZ together), so 50 requests/day is roughly **40 articles/day** after leaving room for
the admin assistant chat. With several hundred items queued from eight feeds, the backlog
is measured in days — which is why topical triage (§2.11) matters as much as throughput:
the budget should be spent on articles this site would actually publish.

## 2. Changes made

### 2.1 Default model is now a free variant

`openai/gpt-4o-mini` (paid, and dead without credit) was the default in five places.
All now resolve to `DEFAULT_AI_MODEL` in [lib/ai.ts](../lib/ai.ts):
**`nvidia/nemotron-3-ultra-550b-a55b:free`**.

Verified against the live catalogue (`GET https://openrouter.ai/api/v1/models`) — 14 `:free`
models exist today. The choice was then made by measurement rather than reputation, with
`npm run check:models` on a real 1292-character article; see the table in §4 for what each
candidate actually produced. `google/gemma-4-31b-it:free` was the provisional pick from the
catalogue alone and lost: it returned `429` from the shared upstream pool on both attempts.

### 2.2 Fallback chain instead of a single model

Free capacity is shared between all OpenRouter users and is frequently busy, so a single
model means dropping to the weak offline heuristics far more often than necessary. The
editorial pass now walks a chain: the configured model, then
`OPENROUTER_FALLBACK_MODELS` (defaults to gpt-oss-20b → nemotron-3-super-120b, ordered by
Uzbek quality rather than speed — see §4).

A model is abandoned and the next one tried on: `429`, `402`, `5xx`, a timeout, an empty
message (reasoning models sometimes spend the whole completion budget thinking), output
that is not JSON, output that is a refusal, or output missing the source language.
`401`/`403` abort the whole chain — a broken key fails identically everywhere, so there is
no point paying one request per candidate to learn that.

### 2.3 Self-healing request shape

The first request per model asks for `response_format: {type: "json_object"}` and
`max_tokens: 8000` (three languages of article body do not fit in the default completion
cap of several free endpoints, which truncates the JSON mid-string). Free endpoints differ
in which parameters they accept, so a `400`/`422` retries the **same** model once with a
plain body rather than treating it as unusable. No hardcoded capability table to go stale.

### 2.4 Reasoning preambles

Most of the free tier is reasoning-tuned and emits `<think>…</think>` before the answer.
Those blocks are stripped before JSON extraction — braces inside the reasoning would
otherwise anchor the brace-slice to the wrong opening brace.

### 2.5 The heuristic fallback no longer spends requests

This was the expensive bug. When the editorial pass failed, the offline fallback path
called the provider **again, once per 450-character chunk** — up to nine extra requests per
article. On a 50-request day that burnt the entire quota on about five articles and then
failed anyway, since a failing editorial call and a failing chunk call almost always share
one cause (rate limit, bad key, data policy).

`translateWithOpenRouterChunk` is gone. The fallback chain is now LibreTranslate →
MyMemory → untranslated source, and the provider is called exactly once per article, by
the editorial pass.

### 2.6 Daily request budget

New table `ai_usage_days` (migration `20260801000000_add_ai_usage_day`) counts requests per
UTC day — the same reset boundary OpenRouter uses. [lib/ai-usage.ts](../lib/ai-usage.ts)
owns it; both the pipeline and the admin assistant chat record against it.

`AI_DAILY_REQUEST_LIMIT` (default **40**, `0` disables metering) caps the pipeline. When the
budget is spent, remaining articles **stay queued** instead of being processed by the
heuristics — they keep their place and get a real editorial pass after the reset. The run
result reports `aiBudget` and splits the batch into `llmArticles` / `heuristicArticles`, so
a run that quietly went all-heuristic is visible instead of being discovered later in the
published output.

A per-article cap (`MAX_REQUESTS_PER_ARTICLE = 3`) stops one stubborn article from eating a
large slice of the day.

### 2.7 Model ids containing `:` were being silently discarded

`normalizeModel` in the assistant route validated ids against `/^[a-z0-9._/-]+$/i`, which
**rejects the colon in every `:free` id** and fell back to the default. Any free model
configured for the assistant chat was silently ignored. `:` is now allowed.

### 2.8 The pipeline had nothing to rewrite (the defect behind everything else)

Measured before any of the above mattered: `scrapeArticleDetails` returned **0 characters
for every configured source**. `lib/scraper.ts` extracted text only from `<p>` elements,
and RIA — one of the three seeded feeds — marks paragraphs up as
`<div class="article__text">` and serves pages with **zero** `<p>` tags. RIA's feed also
carries no `description` at all, so the editorial pass received a bare headline and
invented the rest: asked to produce "3-6 paragraphs" from a 70-character headline, a model
returned a textbook explanation of what lending statistics are.

The extractor was rewritten to work without assuming `<p>`:

1. `articleBody` from JSON-LD, when the site publishes it — the body the publisher itself
   declares, no markup guessing;
2. otherwise, score the known body containers (`[itemprop=articleBody]`, `article`,
   `.article__body`, …) and walk block elements generically, dropping blocks whose text is
   more than 40 % inside links (navigation and "related articles"), and dropping any
   candidate that contains another candidate so wrapper `div`s are not counted twice;
3. otherwise the whole `<body>`.

Result on the same URLs: RIA 0 → **1292** characters (10 paragraphs), Gazeta.uz 0 →
**1671**.

**Thin sources.** Some publishers cannot be scraped at all — TASS article pages return a
1.5 KB bot-block shell. So the prompt now adapts instead of inviting invention:

| Source material | Behaviour |
|---|---|
| ≥ 400 characters | Full article, 3-6 paragraphs |
| 120–400 characters | Brief mode: 1-3 sentences, and the prompt forbids background, context, definitions and consequences |
| < 120 characters | **Not processed at all** — left queued, counted as `skippedThinSource` |

A headline cannot become an article without inventing the article, and a university
masthead cannot publish that.

### 2.9 RSS ingestion rewritten around what feeds actually send

Each configured feed's raw XML was inspected rather than assumed:

| Feed | What it really sends |
|---|---|
| Gazeta.uz | Full lead paragraph — but with `&nbsp;`, `&laquo;`, `&mdash;` **inside CDATA**, which XML parsing does not decode, so those literal characters were being published |
| TASS | One-sentence teaser; no image; article pages bot-blocked |
| RIA | No description whatsoever; image in a typed `enclosure` |
| Reuters | HTTP 404 — dead |
| Kun.uz `/ru` | **Invalid XML** — a bare `&` in a title aborted the parse and lost all 20 items |

Changes to `lib/rss.ts`:

- `content:encoded` and `yandex:full-text` are now captured. Feeds that ship the whole
  article (Times of Central Asia: 10/10 items; UzA: 7-8/20) need **no scraping at all** —
  the text is stored into `rawJson.fullContent`, which the processing step already reads.
- HTML entities are decoded and tags stripped while preserving paragraph breaks.
- Images are resolved from `enclosure`, `media:content`, `media:thumbnail`, `media:group`,
  `itunes:image` and finally an inline `<img>`, and are **type-checked**: a podcast
  `enclosure` of `audio/mpeg` is no longer used as an article photo.
- Invalid XML is repaired once (bare ampersands, forbidden control characters, leading BOM)
  before giving up on a source.
- A feed refresh no longer overwrites an already-scraped body: `rawJson` is merged, and an
  item that stops sending an image no longer blanks the stored one.

`npm run check:rss` locks all of this down with **24 offline assertions**, one per feed
shape above. It parses XML directly rather than serving it over localhost, because the
SSRF guard correctly blocks localhost and weakening a security control for a test is the
wrong trade.

teasers, 27 items carrying full text, 152 of 176 with an image.

### 2.11 The admin's editorial brief now decides what gets published

The brief in Admin → Automation was fed to `deriveTermsFromInstructions`, which turned it
into up to 24 keywords an article had to contain. It failed silently in both directions:

- it stripped everything outside `[a-z0-9]`, so a brief written in **Russian or Uzbek
  produced an empty term list** and filtered nothing at all — with strict mode ticked, the
  admin saw a filter that did precisely nothing;
- it harvested terms from the whole text including negations, so **"avoid politics" added
  *politics* to the list of words an article was required to contain** — the exact inverse
  of the instruction.

Prose about editorial intent needs a model, not a tokenizer. `lib/pipeline/triage.ts` asks
the model to judge each queued headline against the brief, and two design properties matter
more than its accuracy:

**One request per batch, not per article.** Up to 40 headlines go into a single request. At
one request per article, triage would have doubled the cost of everything against a
50-request day; batched, it costs about 1/40th of that and *saves* far more by not writing
articles an editor would reject anyway.

**It fails open.** A rate limit, unparseable output, or an item the model simply omitted all
resolve to "keep it, a human decides". A selection filter that failed closed would silently
stop the site publishing.

Verdicts persist on `ArticleRaw` (`relevance`, `relevanceReason`, `relevanceCheckedAt`, plus
an index) so a rejected headline is never paid for twice. `ids`-targeted runs skip triage
entirely: an editor asking for specific articles outranks the brief.

Live run against the real feeds:

| | |
|---|---|
| Headlines judged | 50, in **one** request |
| Rejected | 28 — weather forecasts, crime and court reporting, sport, foreign lifestyle, a terrorist attack abroad |
| Kept | 22 — presidential diplomacy, energy, rail investment, a youth creative park, regional cooperation |

Each verdict carries its reason ("Weather forecast excluded", "Presidential diplomacy,
regional cooperation"), which is what makes the filter auditable rather than a black box.

The admin UI now separates the two prompts explicitly, because conflating them was half the
problem: the **editorial brief** decides *which* stories are processed, while
**Integrations → AI editorial prompt** decides *how* they are written.

> **Bug found by testing this, worth remembering:** `relevance: { not: "rejected" }` matched
> **nothing**. In SQL `NULL <> 'rejected'` evaluates to NULL rather than true, so every
> un-judged article was excluded and the queue reported "No articles found for processing".
> Both call sites now branch on NULL explicitly.

### 2.12 The About page was publishing fiction

`about_content` is empty, so the page fell through to `defaultAboutPageConfig` — and that
fallback asserted, to the public, on a real university's site: "Established in 1995", the
phone number `+1 (555) 123-4567`, the address "Student Center, Room 304", and a masthead of
**Sarah Connor, James T. Kirk and Nyota Uhura** with invented `@university.edu` addresses.

Replaced with text describing the portal itself (verifiable from this repository), the
university's own published address, and an **empty** masthead. The team block and each
contact block now render only when set — an empty grid under "Meet the Team" reads as broken,
and invented staff is worse than an obviously unfinished page. Confirmed against a running
server: none of those names or numbers appear in the response any more.

The page's configuration also moved out of `contact_messages`, where it lived under the magic
subject `__about_page_config__` and **inserted a new row on every save**, accumulating
internal configuration inside the public inbox forever. New `page_configs` table, upserted;
the migration carries the newest existing value over and deletes the impostor rows. Same
reasoning as moving assistant memory out of that table in `07` §H8.

### 2.13 Empty sections, and why they looked broken

`npm run seed:demo` fills Media, About and Events — idempotently, matching on a natural key
so a second run neither duplicates rows nor overwrites editor changes, and without asserting
anything about the university that is not already public. The photographs are openly-licensed
stock and the script says so in its own output: replace them from Admin → Media.

The underlying UX defect was fixed too, not just the missing data. The homepage rendered its
"Multimedia Highlights" and "Latest Videos" headings above empty grids, and its hero band
showed readers an instruction addressed to an administrator: *"Set media category to
'hero-side' from Admin Media to show content here."* Those sections now render only when they
have content. Media titles are localized, and dates go through `toLocaleDateString` for the
active language instead of being printed as stored strings.

### 2.14 Deployment: three things that stopped it, none of them application code

Opening PR #12 produced a red Vercel check twice, for unrelated reasons. Both are worth
recording because neither was visible from a local build.

**Hobby accounts allow one cron run per day.** `vercel.json` asked for `*/30 * * * *`, and
Vercel rejected the deployment outright — not the cron, the whole deploy. It now schedules
daily, and `.github/workflows/scheduler.yml` calls the same endpoint every 30 minutes
instead; scheduled runs on GitHub are free. The endpoint enforces its own cadence from
`AutomationConfig.fetchPeriodMinutes`, so the extra calls cost nothing — they answer
`period_not_elapsed`. The workflow exits successfully without calling anything until
`APP_URL` and `AUTOMATION_CRON_SECRET` are set, so a fresh clone does not show a
permanently red job.

**Vercel Cron sends GET; the route exported only POST.** In production the scheduled job
would have received `405` and the pipeline would never have run — a failure that produces
no error anywhere, just a site that stops updating. The handler body moved into a shared
`runScheduler` with both verbs exported. Verified against a running server: GET without the
secret is `401`, GET with it is `200` and actually runs the pipeline.

**The build itself required database access, in two places.** The second deployment died in
38 seconds, before compilation:

- `vercel-build` chained `prisma migrate deploy` with `&&`, so an unreachable database
  aborted the deployment with a bare `P1001`, naming neither the setting at fault nor where
  to change it;
- `/sitemap.xml` was prerendered while querying `prisma.article.findMany()`, so the export
  step failed with *"Export encountered an error on /sitemap.xml, exiting the build"* —
  one route that could not read the database was taking the whole site down.

Both were reproduced locally by pointing `DATABASE_URL` at a host that does not resolve.
The sitemap is now `force-dynamic`, which it should have been regardless — a sitemap baked
at build time is stale the moment an article is published — and it falls back to the static
pages instead of a 500 when the query fails. `vercel-build` moved into
`scripts/vercel-build.mjs`, which validates configuration before spending build minutes and
says what to fix. Migrations are still never skipped when a database is configured:
deploying code whose schema was not applied is worse than a failed build.

> A green Vercel check no longer means a working site. The build deliberately succeeds
> without a database, so the environment variables below still have to be right.

### 2.15 Two defects found by automated review

- **The approvals migration locked every existing administrator out.** `approved` and
  `isSuperAdmin` were added defaulting to `false`, while the same release refuses login
  unless `approved` and requires `isSuperAdmin` to reach `/api/admin/users` — nobody can
  sign in and nobody can approve anybody. Migration `20260801140000_backfill_admin_approval`
  re-approves accounts created before 2026-07-31 and promotes the earliest account if no
  approved super-admin exists. Scoped by date on purpose: accounts created *after* approvals
  existed went through signup and must still wait for a human. The lockout was reproduced
  against the live database and the backfill confirmed to restore access.
- **The last super-admin could demote themselves.** `toggle_super` guarded only the
  hardcoded bootstrap email, which is configurable; when it differs, the final super-admin
  could remove their own privilege and `checkSuperAdmin` would then reject everyone. It now
  counts approved super-admins, mirroring the guard the delete handler already had.

### 2.16 Every public page now owns its metadata

Five of the six public pages were client components, and a client component cannot export
`metadata`. All of them therefore inherited the root layout's defaults: one title, one
description, and a canonical URL pointing at `/`. For a news site that collapses the whole
domain to a single search result and makes every social share render the site-wide card.

Each route gained a thin server wrapper that owns its metadata and renders the client
component underneath. Measured against a running server, before → after:

| Route | Title before | Canonical before | Title after | Canonical after |
|---|---|---|---|---|
| `/news` | Media Uwed | `/` | News \| Media Uwed | `/news` |
| `/events` | Media Uwed | `/` | Events \| Media Uwed | `/events` |
| `/media` | Media Uwed | `/` | Media gallery \| Media Uwed | `/media` |
| `/about` | Media Uwed | `/` | About \| Media Uwed | `/about` |
| `/contact` | Media Uwed | `/` | Contact \| Media Uwed | `/contact` |

One set of tags per route, not per language: the language switch is client-side, so
per-language metadata needs language-prefixed routes (`/en/news`), still in the backlog.

The news archive was also still in English on a trilingual site — "News Archive", "Show
filters", "Read More", "By <author>", the empty state and the loading text — and printed
dates as the raw stored string. All localized, dates through `toLocaleDateString` for the
active language.

### 2.17 The admin could not see what the pipeline did

All 15 admin screens and every GET endpoint were exercised with a real session: nothing was
broken. The gap was elsewhere. The pipeline reports off-brief rejections, the split between
the model and the offline heuristics, headline-only skips, the remaining daily budget and
per-feed failures — and **none of it reached the screen**. Every run collapsed into a toast
reading "Processing complete: N items processed", gone in seconds. A run that quietly
produced nothing looked identical to a healthy one, and a feed returning 404 was invisible
because the run still succeeded.

Admin → Automation now shows a last-run panel: feed errors listed individually, the
heuristic count highlighted (that output is publishable but visibly weaker, so it must not
be silent), off-brief and thin-source counts, and a daily-budget bar that turns red when
spent.

Triage verdicts were invisible **and** irreversible — an off-brief article simply vanished
from the queue. There is now a "Show off-brief (N)" toggle, a reason badge on each rejected
item, and a restore action (`PATCH /api/admin/automation/raw`) that clears the verdict so
the next run reconsiders it. A model's opinion about an editor's brief has to be reversible
by the editor.

Verified end to end: the default queue hid 48 rejected items with none leaking,
`showRejected=1` revealed them with their reasons, and restoring one returned it to the
default queue and dropped the count to 47.

### 2.18 The security primitives had no tests at all

`lib/security.ts` encrypts every provider API key and Telegram token in the database, and
`lib/admin-auth.ts` decides who is an administrator. Neither had a single test — the worst
place in this codebase for that, because both fail invisibly: a tampered ciphertext that
still decrypts, or a forged token that still verifies, look exactly like normal operation
until somebody exploits them.

`npm run check:security` adds 41 assertions about properties rather than implementation:

- authenticated encryption actually authenticates — a flipped byte in the ciphertext, the
  auth tag or the IV must each be rejected, not silently decrypted;
- a fresh IV per call, so two integrations sharing a key are not identifiable by matching
  ciphertext in the database;
- passwords are salted (identical passwords hash differently) and malformed or truncated
  hashes are rejected rather than throwing;
- session tokens reject the forgery that matters — a payload rewritten to claim
  `role=superadmin` while keeping the genuine signature — and an expired token whose
  signature is perfectly valid;
- sessions issued before a password change are stale, including legacy tokens with no `iat`.

**One assertion failed, and the code was wrong, not the test.** `decryptSecret` guarded with
`if (!ivPart || !tagPart || !contentPart) return null`, so a payload from
`encryptSecret("")` — structurally valid, with an empty ciphertext — was reported as
corrupt. The guard now checks structure (three parts, non-empty IV and tag) and lets an
empty payload decrypt to an empty string. Verified that the stored OpenRouter key still
decrypts before and after; callers already normalise with `(value || "").trim()`.

### 2.19 Two settings that did nothing, and logs that could not be followed

Settings offered "Enable comments on articles" and "Moderate comments before publishing".
There is no comment model, no endpoint and nothing rendering comments on the site: ticking
either did nothing at all. A control that silently does nothing is worse than a missing
feature — it tells the operator the site behaves in a way it does not. Both removed from the
UI; the columns remain on `SiteSettings`, annotated `NOT IMPLEMENTED`, and the form still
round-trips their stored values so saving settings does not reset them.

Logging: a single pipeline run emits triage verdicts, per-model fallback attempts, budget
warnings and scraper failures — and runs overlap, between the scheduler, an admin pressing
Process, and a cron call. In a hosting log viewer those lines interleave with no way to tell
which "AI editorial pass failed" belongs to which run. The logger now carries a request id
through `AsyncLocalStorage`, preferring an id the platform already assigned (`x-vercel-id`,
`x-request-id`, `cf-ray`) so traces line up, and all four cron routes are wrapped.

Proving that required fixing something first: `runPull` never used the structured logger at
all, only one `console.error`, so there was nothing to correlate. Feed pulls now log a run
summary, and the remaining `console.*` calls in `pull.ts`, `rss.ts` and `scraper.ts` are
structured logger calls carrying the feed and article URLs.

Verified with two concurrent pull runs: two distinct request ids, each line attributable to
its own run, where the two summaries had previously been indistinguishable.

### 2.20 One backlog item closed by measurement rather than by work

The first audit listed the global-context over-fetch among its main findings. Measured before
touching it: the whole bootstrap transfers **17 KB** per page load — articles 6 KB, events
4.5 KB, media 3.2 KB, about 3.8 KB. That does not justify refactoring a provider twenty files
depend on, so the item is closed as immaterial rather than left open indefinitely. A backlog
that only ever grows stops being a plan.

3. **Route tests cover authorization only.** `npm run check:routes` asserts that all nine
   content mutations, ten admin endpoints and four cron routes refuse anonymous callers, that
   a wrong cron secret is rejected, that the removed seed backdoor stays removed, and that
   login is rate limited — 37 assertions, validated by deliberately removing a guard and
   confirming the suite fails. What it does **not** cover is the behaviour behind those
   routes: nothing asserts that publishing an article produces the right row.
4. **Full-text search.** `/news` search is still `contains`. At a few hundred articles that
   is fine — worth an index when the archive grows, and worth measuring first.
5. `M4`: `app/admin/(protected)/automation/page.tsx` has grown to ~1700 lines.

### Still open — environment, not code

7. **`DATABASE_URL` must be a managed Postgres reachable from the deployment platform.**
   A value copied from a local `.env` (`@localhost:5432`) cannot work in a build container,
   where `localhost` is the container itself. The build now fails with that explanation
   rather than a bare `P1001`.
8. **`APP_URL` / `NEXT_PUBLIC_SITE_URL` are unset**, so canonical links, Open Graph tags,
   `sitemap.xml`, Telegram post links and password-reset emails all point at localhost.
9. **The 30-minute cadence needs two GitHub Actions secrets** — `APP_URL` and
   `AUTOMATION_CRON_SECRET` — because Vercel's Hobby plan only allows a daily cron. Without
   them the pipeline runs once a day.
10. **`uwed.uz` has no RSS feed** (404 on `/rss` and `/feed`), so the university's own news
    must be entered by hand until a feed exists on their side.
11. **The repository must stay on an NTFS volume.** A copy still exists on the exFAT `D:`
   drive, where `next build` cannot work at all — see `07` §C5 for the mechanism.

### Operational notes

- **Check OpenRouter → Settings → Privacy** if a model returns `404` with a data-policy
  message: there are separate toggles for free and paid models.
- **$10 of credit** raises the daily cap from 50 to 1000 requests (one-time, not a
  subscription). Then raise or zero `AI_DAILY_REQUEST_LIMIT`.
- **Uzbek quality is imperfect on free models.** Observed in a live run:
  "223 ta **ukrayna** dronlarini" (should be *Ukraina*), "**moscva** vaqti",
  "ro'yx**siz**". Readable and factually right, but every article needs an editor — which
  is why they land in `pending_review` rather than being published.

| Variable | Default | Purpose |
|---|---|---|
| `OPENROUTER_API_KEY` | — | Fallback key when none is stored in the admin UI |
| `OPENROUTER_TRANSLATE_MODEL` | `nvidia/nemotron-3-ultra-550b-a55b:free` | Editorial pass model |
| `OPENROUTER_ASSISTANT_MODEL` | `nvidia/nemotron-3-ultra-550b-a55b:free` | Admin assistant chat model |

| `DATABASE_URL` | — | **Required.** Must be reachable from the build container; `localhost` cannot work there |
| `APP_URL` / `NEXT_PUBLIC_SITE_URL` | — | Canonical links, Open Graph, sitemap, Telegram links |
| `AUTOMATION_CRON_SECRET` | — | Guards `/api/cron/*`; also needed as a GitHub Actions secret for the 30-minute scheduler |

The model stored in Admin → Automation → Integrations takes precedence over
`OPENROUTER_TRANSLATE_MODEL`, which takes precedence over the built-in default.
